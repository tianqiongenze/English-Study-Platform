## 3. 契约测试(P1: Pact for Dubbo esp-api)

### 3.1 实现方式

Dubbo Triple 无原生 Pact HTTP transport,采用 **file-based Pact + JVM 级 provider 验证**:

- **Consumer 侧**(teacher-java):`LearningRpcPactConsumerTest` 用 `PactDslJsonBody` 定义 `LearningRpcService.userStats(Long)` 响应的期望结构(KpStat 数组,4 字段类型约束),生成 pact JSON 文件到 `services/teacher-java/target/pacts/teacher-learningrpc-pact.json`。同时验证 KpStat 反序列化/序列化字段完整性。
- **Provider 侧**(learning-java):`LearningRpcPactProviderTest` 读取 consumer 生成的 pact 文件(文件系统路径 fallback 到 classpath),用真实 `LearningRpcProvider`(mock `LearningService`,复用 `LearningRpcProviderTest` 的 mock 方式)调用 `userStats(42)`,逐字段比对 provider 输出与 pact 期望体。

依赖:`au.com.dius.pact.consumer:junit5:4.6.16`(consumer) / `au.com.dius.pact.provider:junit5:4.6.16`(provider)。

### 3.2 覆盖的 interaction

| Consumer | Provider | Method | 期望 |
|---|---|---|---|
| teacher-java | learning-java-LearningRpcService | `userStats(userId=42)` | `List<KpStat>`: kpId(integer), masteryScore(decimal), reviewCount(integer), nextReviewAt(string/null) |

仅覆盖 consumer 实际使用的 `userStats`;`weakCount` 未被 consumer 调用,不在契约测试范围内。

### 3.3 CI 运行

在 `.github/workflows/ci.yml` 的 `contract` job 中执行:

1. Consumer(teacher-java)跑 pact consumer test,生成 pact 文件
2. 拷贝 pact 文件到 provider 的 classpath fallback 位置
3. Provider(learning-java)跑 pact provider verify,读取 pact 文件做契约比对

依赖顺序:consumer 必须先于 provider 执行(生成 pact 文件供 provider 消费)。

### 3.4 测试结果

- Consumer: 3 tests, 0 failures (RC=0)
- Provider: 3 tests, 0 failures (RC=0)
- Pact 文件: `services/teacher-java/target/pacts/teacher-learningrpc-pact.json` (833 bytes)

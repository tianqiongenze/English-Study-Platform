# 日志系统架构(ADR-observability-rebuild)

> 更新:2026-08-01。范围:全平台(三端 + BFF + 5 后端服务 + 基础设施)日志收集、结构化日志分析、用户行为分析与推荐。

## 0. 一句话结论(回答用户)

- **日志系统完善了吗?** —— 重构前**不完善**:可观测栈 manifest 存在但全 0/0 未起;各服务仅 stdout 打日志无统一采集;无结构化业务日志表;前端用户行为事件仅 `/api/learning/event` 一条上报路径且 payload 单一、未做行为分析。**本重构实现双轨日志 + 用户行为分析 + 推荐端点**,manifest/代码/配置就绪(资源紧张暂不全 scale)。
- **日志分析能用 TiDB 吗?** —— **能,但仅存结构化日志**(业务事件/行为/审计/鉴权/批改)。TiDB 行存 + Raft 三副本写放大不适合存原始容器日志高吞吐追加写;原始日志走 Loki(仅索引标签,成本约 1/10)。TiKV 是 TiDB 的存储引擎不独立暴露,日志经 TiDB SQL 接口即可,无需直连 TiKV。

## 1. 双轨架构

```
┌─────────────────────────────── 原始日志轨(运维排障)───────────────────────────────┐
│ 容器 stdout/stderr ─Fluent Bit DaemonSet(tail /var/log/containers/*.log)           │
│   ─ K8s filter 提取 esp_app/esp_ns 标签 ─OUTPUT Loki(仅索引标签,7d 保留)            │
│ Grafana → Loki(LogQL 查询,trace_id 标签关联)                                          │
└──────────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────── 结构化日志轨(业务分析)──────────────────────────────┐
│ 三端(Web/H5/小程序)用户行为事件 ─POST /api/learning/event(已存在,扩展 payload)       │
│   + /api/learning/behavior(新增:统一行为上报,见 §4)                                  │
│ BFF/learning/teacher/writing/emotion/gateway 关键业务点                                │
│   ─ AppLogClient(异步,Disruptor/线程池,降级不阻断业务)─ INSERT app_logs(TiDB 主)     │
│ 分析查询 ─ TiDB follower(读副本)─ SQL 聚合(见 §5)─ Grafana SQL 数据源 / API          │
└──────────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────── 链路关联(OTel traceId)───────────────────────────────┐
│ 三端注入 traceparent(W3C)→ BFF → 下游服务,贯穿 app_logs.trace_id 与 Loki 日志         │
│ OTel Collector(esp-observability:4317)→ Tempo;Tempo/Grafana 关联 trace                │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

## 2. 选型理由

| 维度 | 原始日志 → Loki | 结构化日志 → TiDB |
|---|---|---|
| 数据特征 | 高吞吐追加写、文本、低价值密度 | 低中吞吐、JSON、高价值可聚合 |
| 索引 | 仅标签(app/ns/level/trace_id) | 多列索引 + JSON 函数索引 |
| 成本 | ~1/10 全文索引(ES)方案 | 复用已有 TiDB 集群,零增量基础设施 |
| 查询 | LogQL(正则过滤、流式) | SQL(GROUP BY / 窗口 / JOIN) |
| 保留 | 7 天(retention_period: 168h) | 长期(可分区归档) |
| 典型用例 | "gateway-go 昨晚 23:00 的 ERROR 堆栈" | "近 1 天 writing.grade 平均耗时 / 学情事件 TOP 用户 / 近 7 天登录失败 TOP5 IP" |

**为何不直存 TiKV**:TiKV 是 TiDB 的分布式 KV 存储引擎,不独立暴露客户端 API;日志经 TiDB SQL 接口即可享受 ACID + 二级索引 + 读写分离,无需绕过 TiDB 直连 TiKV(否则失去索引/事务/SQL 能力,自行维护 Raft 复杂度更高)。

**为何原始日志不进 TiDB**:原始容器日志高吞吐(全平台 6 服务 × stdout,峰值千行/秒)追加写 + Raft 三副本写放大,会拖垮 TiDB 写延迟;Loki 仅索引标签、chunk 压缩追加,契合该负载。

## 3. app_logs 表(TiDB 结构化日志)

见 `docs/design/schema.sql` 末尾追加。字段:`id/ ts/ service/ level/ event/ trace_id/ user_id/ payload(JSON)/`。索引:`idx_ts`、`idx_service_event`、`idx_trace`、`idx_user_event`。写主(tidb-primary),分析读走 follower(tidb-follower)。

## 4. 用户行为分析与推荐

### 4.1 现状(重构前)
- 仅 `frontend-react`/`frontend-h5`/`frontend-miniprogram` 三端 `reportEvent()` → `POST /api/learning/event`(event_type/payload 字符串),**只存 `learning_events` 表,无聚合分析、无推荐端点**。
- 无统一行为上报(点击/停留/完成/退出/语音时长等);无后端分析 API;无推荐。

### 4.2 重构实现
1. **统一行为上报端点**(新增):`POST /api/learning/behavior` —— 三端调,字段 `{user_id, action, target, duration_ms, context{...}, ts}`,落 `app_logs`(event=`behavior.*`)。复用 `learning_events` 不变,行为事件双写 `app_logs` 以便跨服务统一分析。
2. **行为分析 API**(新增,learning-java):
   - `GET /api/learning/behavior/top?days=7&limit=10` —— 近 N 天活跃 TOP 用户(SQL 聚合 app_logs)。
   - `GET /api/learning/behavior/funnel?action=enter_speech,practice,complete&days=7` —— 漏斗分析。
   - `GET /api/learning/behavior/heatmap?user_id=X&days=30` —— 用户行为热力(按 event 分组计数)。
3. **相关推荐 API**(新增,learning-java):`GET /api/learning/recommend?user_id=X` —— 基于用户行为(薄弱知识点 + 历史练习事件 + 场景偏好)推荐:
   - 复习清单(已有 `dueReview` Ebbinghaus 调度);
   - 相似用户练习过的场景(基于 scenario + user_mastery 协同过滤,轻量 SQL);
   - 写作练习推荐(基于最近 writing.grade 评分低的维度)。
4. **三端接入**:三端 `api.ts` 增 `reportBehavior()` + `getRecommendations()`;LearningPanel 展示"为你推荐"卡片。

## 5. 典型分析 SQL(走 follower 读副本)

```sql
-- 近 1 天 writing.grade 平均耗时 + P95
SELECT AVG(JSON_EXTRACT(payload,'$.duration_ms')) avg_ms,
       PERCENTILE_CONT(JSON_EXTRACT(payload,'$.duration_ms'),0.95) p95
FROM app_logs WHERE service='writing' AND event='writing.grade' AND ts> NOW()-INTERVAL 1 DAY;

-- 学情事件 TOP5 用户(近 7 天)
SELECT user_id, COUNT(*) cnt FROM app_logs
WHERE service='learning' AND event='learning.event' AND ts> NOW()-INTERVAL 7 DAY
GROUP BY user_id ORDER BY cnt DESC LIMIT 5;

-- 登录失败 TOP5 IP(审计/安全)
SELECT JSON_EXTRACT(payload,'$.ip') ip, COUNT(*) cnt FROM app_logs
WHERE service='bff' AND event='auth.login' AND level='WARN' AND ts> NOW()-INTERVAL 7 DAY
GROUP BY ip ORDER BY cnt DESC LIMIT 5;
```

## 6. 降级策略
- AppLogClient(TiDB 写)失败:仅 `log.warn`,**不阻断业务主路径**(参考 esp-cache 降级模式)。
- Loki 不可用:Fluent Bit 重试 + 本地 positions 缓存,不影响服务。
- OTel Collector 不可用:各服务 tracing.go/tracing.py 已有 no-op 降级(gateway-go 显式 `WithInsecure` + 失败返 no-op shutdown;writing-py `setup_tracing` 幂等)。

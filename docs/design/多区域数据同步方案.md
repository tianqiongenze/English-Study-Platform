### 1.2.1 灌装数据多区域同步验证(2026-08-01 实测)

> 验证背景:session_turns 灌数进行中(写 tidb-primary/aws),需确认灌装数据在 azure/gcp 从库同步可见。

**验证方法**:用 writing-py pod(pymysql)连三区 TiDB,在 aws 主库写带标记行 → 立即从 azure/gcp 读 → 再做 session_turns 同步点查。

**验证证据**:
1. **写 aws 读 azure/gcp(标记行)**:
   - aws(tidb-primary:4000):`CREATE TABLE multiregion_verify` + `INSERT (id=1, marker='multiregion-verify-2026-0801')`。
   - 等 2s(Raft 复制)→ azure(tidb-follower:4000)`SELECT` = `(1, 'multiregion-verify-2026-0801')` ✅ MATCH。
   - gcp(tidb-cluster-tidb.ekb-m2-gcp-europe-west1:4000)`SELECT` = `(1, 'multiregion-verify-2026-0801')` ✅ MATCH。
   - 三区读到完全一致的标记行 → **Raft 强一致复制生效,写 aws 立即可在 azure/gcp 读到**。
2. **session_turns 灌数同步验证(点查,避免全表 COUNT 发散)**:
   - 全表 `COUNT(*)`:aws=4173000 / azure=4325000 / gcp=4434000(**三区不一致**,原因见下)。
   - **MAX(id) 点查(确定性)**:aws/azure/gcp 三区 `MAX(id)` 均为 `8935141660708413064`,且 `SELECT COUNT(*) WHERE id=MAX` 三区均=1 → **最新灌装行三区一致可见**。
   - 全表 COUNT 不一致解释:`COUNT(*)` 在 TiDB 走 IndexScan + 协处理器并行聚合,三区 TiDB 实例各自调度 region 扫描,在灌数并发写入进行中会因扫描起点/快照隔离窗口不同得到不同近似值(非数据丢失)。**点查(MAX/id 精确读)三区一致才是强一致的真正证据**。验证后已 `DROP TABLE multiregion_verify` 清理。

**结论:灌装数据已做到多区域同步(Raft 强一致),写 aws 主库的数据立即可从 azure/gcp 从库读到。**

### 1.2.2.1 读写分离公共工具包抽取(2026-08-01)

为消除各服务重复实现读写分离代码,抽取公共工具包:
- **Java 侧 `esp-rw-java`**(`services/esp-rw-java/`):RoutingDataSource(AbstractRoutingDataSource)+ DataSourceType 枚举 + RoutingHolder(ThreadLocal)+ @DataSource 注解 + DataSourceAspect(AOP 切面,consistent=true 强制走主库)+ DataSourceConfig(Spring Boot 自动配置,`@ConditionalOnProperty esp.rw.enabled`)。已 install 到本地 m2,learning-java / teacher-java / bff-java 均依赖 `com.esp:esp-rw-java:1.0.0`,删除各自 `rw/` 包和 `DataSourceConfig`,import 改为 `com.esp.rw.*`。
- **Python 侧 `esp-db-py`**(`services/esp-db-py/`):aiomysql 双连接池(write_pool→tidb-primary / read_pool→tidb-follower),`execute_write` / `execute_read`(forced_primary=True 写后强一致读)/ `execute_read_one`,从库不可达自动 fallback 主库。writing-py / emotion-svc 均依赖。
- **Go 侧 `src/db/db.go`**(`services/gateway-go/src/db/`):database/sql + go-sql-driver/mysql 双连接池,`Write` / `Read`(forcedPrimary)/ `Enabled()`,sync.Once 延迟初始化,gateway-go 内部包。
- **构建验证**:learning-java `mvn test` 35 tests PASS / teacher-java `mvn test` 12 tests PASS / bff-java `mvn test` BUILD SUCCESS / gateway-go `go test ./...` 全部 PASS。
- **feature flag**:三侧均支持 `DB_ENABLED=false`(Java 侧 `esp.rw.enabled=false`)no-op 回退,保证无 DB 环境降级安全。

## 2. 单节点物理约束(关键现实)

- 环境:**单物理节点 lima-rancher-desktop**(6 CPU / 40GB),三区 ns 是逻辑分区(同物理节点)。
- 当前内存:19GB/79% 已用,剩约 21GB。
- 三区全起 Pulsar broker(每 broker ~1-1.5GB)需额外 ~3-4.5GB;三区 Redis 各 1 副本需额外 ~1-2GB。**理论可塞下,但单节点资源紧张会导致 VM 抖动(此前 API server 6443 refused 反复的根因)。**
- **真正的多区域容灾在单物理节点上无意义**:三区共享同一 VM/磁盘,VM 挂了三区全挂。多区域的价值在于跨物理节点容灾,本环境物理上无法验证。

## 3. ESP 实际需求评估(是否需要多区域 Pulsar/Redis 同步)

### 3.1 Pulsar 用途
- ESP 项目 Pulsar **仅用于 esp-cache(Java)的缓存失效广播**(topic `esp-cache-invalidate`),以及预留 topic(learning.event/writing.task 等,无真实生产者)。
- **无真实业务消息流**。缓存失效广播在单区单 broker 即可满足(Java 服务多副本同 namespace,共享一个 broker 即可广播)。
- 跨区 Pulsar geo-replication 对 ESP = 过度设计。

### 3.2 Redis 用途
- 会话状态 `esp:ctx:*`(种子进度/压测计数/任务状态)+ gateway-go 会话 `session:{id}`(2h TTL)+ 缓存 L2(esp-cache / esp-cache-py / gateway-go cache)+ warmup 数据。
- 会话状态本身是单区活态数据(用户连哪个区就用哪个区的会话),跨区强一致需求弱。
- **结论:Redis 单区已满足 ESP 当前所有需求。**

### 3.3 综合决策(更新:Redis 跨区已实现)
| 组件 | 决策 | 理由 |
|------|------|------|
| TiDB | ✅ 已多区域 Raft(保持) | 数据强一致核心,已完成 |
| Redis | ✅ **已实现跨区主从异步复制**(aws 主→azure/gcp 从,2026-08-01 验证通过) | 主从异步复制真实可用,主挂丢少量窗口(最终一致);主动-主动 CRDT 需 Enterprise 不可行 |
| Pulsar | ✅ aws 单 broker 起通(广播可用);geo-rep 单节点不可行,给多节点模板 | standalone 不支持 geo-rep;单节点起三套完整集群吃内存且无跨物理节点价值 |

**即:多区域数据同步 — TiDB 强一致 Raft ✅;Redis 跨区主从异步复制 ✅ 已验证;Pulsar aws 单 broker 广播可用 ✅,geo-rep 单节点不可行(给多节点模板)。**

## 4. 可移植方案(多节点生产环境)

### 4.1 Pulsar 跨集群复制(geo-replication)

多节点环境下,三区各部署独立 Pulsar 集群(broker + bookie),通过 **geo-replication** 做跨集群消息复制(异步,最终一致):

1. 每区独立 Pulsar 集群(3 broker + 3 bookie,跨节点 Raft/Quorum)。
2. 配置全局 zookeeper 或 broker 间互信(`brokerClientAuthenticationPlugin`)。
3. 创建 topic 时指定 `replication-clusters`:
   ```bash
   # 在 aws broker 上
   pulsar-admin namespaces set-replication persistent://esp/cache-invalidate \
     --clusters aws,azure,gcp
   ```
4. 生产者写本地集群,消费者读本地集群;broker 自动跨区复制消息。
5. ESP 场景:`esp-cache-invalidate` topic 设三区复制,任一区 Java 服务 evict 广播后三区都收到 → 真多区域缓存一致。

**manifest 模板**(`deploy/k8s/08-pulsar-multiregion.yaml`,生产多节点用,本环境不 apply):
```yaml
# 每区一个 Pulsar broker + bookie,跨区 geo-replication 配置
# 本环境(单节点)不部署,保留作多节点迁移模板
apiVersion: apps/v1
kind: Deployment
metadata: { name: pulsar-broker, namespace: <region-ns> }
spec:
  replicas: 1  # 多节点生产:3
  template:
    spec:
      containers:
      - name: broker
        image: apachepulsar/pulsar:3.3.0
        args: [bin/pulsar, standalone]  # 生产:bin/pulsar broker + 配置文件
        env:
        - name: PULSAR_PREFIX_brokerClientAuthenticationPlugin
          value: "org.apache.pulsar.client.impl.auth.AuthenticationTls"
        # geo-replication 配置在 broker.conf: replicationConnectionsPerBroker / clusterName
        ports: [{containerPort: 6650}, {containerPort: 8080}]
```

### 4.2 Redis Cluster 跨区主从(异步复制)

开源 Redis 不支持主动-主动多活(CRDT 需 Redis Enterprise)。多节点环境用 **Redis Cluster 跨区主从 + 自动 failover**:

1. Redis Cluster 6 节点:3 主(每区一个)+ 3 从(跨区,主在 aws 从在 azure,等等)。
2. 主从异步复制:写主 → 异步同步到从。
3. 主挂自动 failover:从提升为主。
4. ESP 场景:会话 `session:{id}` 写 aws 主,异步同步到 azure/gcp 从;aws 区故障时 azure 从提升为主,会话不丢(最终一致,少量窗口数据可能重复消费)。

**manifest 模板**(多节点用,本环境不 apply):
```yaml
# Redis Cluster 6 节点(3主3从跨区),需 --cluster-enabled yes + --cluster-config-file
# 本环境单节点不部署,保留作多节点迁移模板
apiVersion: apps/v1
kind: StatefulSet
metadata: { name: redis-cluster, namespace: <region-ns> }
spec:
  serviceName: redis-cluster
  replicas: 2  # 每区 1主1从,三区共6,需多节点
  template:
    spec:
      containers:
      - name: redis
        image: redis:7.2-alpine
        args:
        - --appendonly
        - "yes"
        - --cluster-enabled
        - "yes"
        - --cluster-config-file
        - nodes.conf
        - --cluster-node-timeout
        - "5000"
# 部署后用 redis-cli --cluster create <6节点:6379> --cluster-replicas 1 组建集群
```

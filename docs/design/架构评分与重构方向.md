## 二、子系统/模块/公共包划分是否符合大厂标准

### 2.1 现状(12 个 services/ 子目录)

| 分类 | 模块 | 语言 | 单测数 | 评价 |
|---|---|---|---|---|
| 业务服务 | gateway-go | Go | 5 | ✅ 边界清晰 |
| | bff-java | Java | **0** | ⚠ 零单测,鉴权/JWT 核心无覆盖 |
| | learning-java | Java | 7 | ✅ |
| | teacher-java | Java | 2 | ⚠ 偏少 |
| | writing-py | Python | 7 | ✅ |
| | emotion-svc | Python | 6 | ✅ |
| 公共包 | esp-api | Java(Dubbo 契约) | 0 | ✅ 纯接口包,合理 |
| | esp-disruptor | Java | 0 | ⚠ 核心环形缓冲无单测 |
| | esp-rw-java | Java | 0 | ⚠ 读写分离路由核心无单测(集成测覆盖) |
| | esp-cache | Java | 0 | ⚠ 缓存广播无单测 |
| | esp-cache-py | Python | 0 | ⚠ **与 esp-cache 两套缓存抽象,职责重叠** |
| | esp-db-py | Python | 0 | ⚠ 读写分离核心无单测 |

### 2.2 大厂标准对照

**符合的**:
- ✅ 公共能力下沉为独立 artifact(esp-rw-java / esp-db-py / esp-cache),业务服务依赖而非复制 —— 这是大厂标准做法。
- ✅ Dubbo 契约独立 esp-api 包(provider/consumer 共享接口),契约与实现分离。
- ✅ 多语言按"实时面/业务面/AI 面"选型,每语言一个公共包(DB/cache),符合 polyglot 微服务规范。

**不符合 / 缺口**:
1. **❌ 缺契约测试(Pact)**:esp-api 是 Dubbo 接口包,但无 consumer-driven contract test。大厂标准:provider CI 验证 consumer pact,改接口破坏契约时 CI 红。当前靠人工联调,接口漂移风险高(压测中 INT-2 Dubbo timeout 3s→10s 就是隐性契约破坏)。
2. **❌ 缺 CI/CD pipeline**:无 `.github/workflows`、无 Jenkinsfile。大厂标准:每个 MR 跑 unit+contract+lint+镜像构建,gate deploy。当前全靠手动 `mvn test` / `go test`,无自动化质量门禁。
3. **❌ 公共包零单测**:esp-disruptor(核心环形缓冲)、esp-rw-java(路由数据源)、esp-cache(广播失效)三个最该测的公共包 0 单测。大厂标准:公共库覆盖率 ≥90%(被多服务依赖,bug 放大)。
4. **⚠ esp-cache(Java)与 esp-cache-py(Python)两套独立缓存抽象**:L1+L2 语义各自实现,key 规范不统一(Java 完整 key vs Python/Go sha256)。大厂标准:跨语言共享**契约(接口签名 + key 规范文档)**,实现各自语言最优,但 key 必须一致。当前三端 key 割裂,跨语言缓存共享会脏读。
5. **⚠ bff-java 零单测**:鉴权(JWT 签发/校验)、X-User-Id 注入、限流这些安全核心零覆盖。大厂标准:安全相关代码覆盖率 100%。
6. **⚠ 缺 PreStop / graceful shutdown**:`terminationGracePeriodSeconds` 默认 30s,但 WebSocket 长连接(gateway-go)和 Disruptor 在途事件(learning-java)未配置 preStop drain。大厂标准:长连接/有状态服务必须 preStop 主动 drain + 注销。

### 2.3 结论

**子系统/公共包的"划分粒度"基本符合大厂标准**(公共能力下沉 + 契约独立 + 多语言公共包),但**"质量保障工程化"明显不达标**:零 CI/CD、零契约测试、公共包零单测、安全核心零覆盖。这是从"能跑的 demo"到"可上线产品"最大的工程化缺口。

## 三、5000 CCU 实压测暴露的真瓶颈(2026-08-02 实测)

> 压测环境:单节点 Rancher Desktop,集群内 locust-runner pod(locust 2.31.5),入口 Traefik ClusterIP + Host 头。
> 三轮:tierA2(1000 CCU 90s 探针修复后)、tierB(5000 CCU 230s seata 抖动期)、tierC(5000 CCU 220s seata 探针修复后)。

| 场景 | 吞吐 | P95 | 失败率 | 主要失败 | 根因 |
|---|---|---|---|---|---|
| 1000 CCU(tierA2) | 790 rps | 1.3s | 0.001% | 1×502 | 探针修复后基本健康 |
| 5000 CCU(tierC) | **533 rps** | **25s** | **7.3%** | writing 503/502(1934)、teacher 503(1895)、learning 502/500(154) | 下游服务被打满 + seata 探针误杀 |

**暴露的 4 个真问题**:
1. **探针在高负载下误杀(gateway-go r=9/10、seata r=8)**:`/healthz` timeout=1s 在高并发下来不及应答 → liveness 杀 pod → 连接中断 + 冷启动 + HPA 抓不到持续高 CPU 不扩容。**已修**(timeout 1→3s、period 10→15s、failureThreshold 3→5),但属"事后补救",设计期应按大厂标准三探针分离(startup/liveness/readiness)。
2. **writing-py / teacher-java 在 5000 CCU 下 503/502 高发**:writing-py max latency 112s(LLM 调用阻塞 worker),teacher-java 503(HPA 扩到 2 但新 pod 启动期不可用)。根因:AI 推理长尾 + 单节点资源不足,HPA 扩容速度跟不上。
3. **HPA 扩容但不健康**:learning-java HPA 扩到 4,但 3 个新 pod ready=false(启动期 Nacos/Dubbo 注册慢 + 资源争抢)。单节点资源瓶颈,多节点可缓解。
4. **单节点扛不住 5000 CCU**:这是环境约束非设计缺陷,但**压测脚本本身在单节点跑 locust 也吃资源**,测的是"单节点 + 被测系统 + 压测机同节点"的混合上限,非纯系统上限。生产必须分布式 Locust master+workers 独立节点。

**未达标的 SLO**:G-01(5000 CCU,单节点不可达)、G-04(写作 50rps,实测 47rps 接近但 P95 73s 远超 2s)、G-06(学情 5000 ev/s,实测 277 ev/s)。G-02(口语 P95<800ms,scenarios P95 15s,但非真实 ASR/LLM/TTS 链路)。

5. **❌ 契约测试(Pact)**:Dubbo esp-api 接口 consumer-driven contract,provider CI 验证。

6. ⚠ soak 测试(8h 长稳,查内存泄漏/GC 抖动)。

10. ⚠ preStop + graceful shutdown(gateway-go WS drain、learning-java Disruptor drain)。

## 六、本轮可落地的经验沉淀(详见 §七)

本轮压测暴露的 3 个可复用教训:
1. **探针 timeout 不能用默认 1s**:高负载下 `/healthz` 来不及应答 → liveness 误杀 → 雪崩。设计期按三探针分离 + timeout≥3s。
2. **压测机不能与被测系统同节点**:单节点跑 locust 测的是混合上限,非系统上限。生产用独立 Locust 节点。
3. **HPA 扩容速度 < 流量突增速度**:AI 推理长尾 + 新 pod 启动慢(注册/资源争抢)导致扩容跟不上,需预热(surge)或队列削峰。

## 附 §A:2026 最佳实践对照(联网调研,subagent 产出)

> 完整 checklist 见本文末"架构最佳实践参考(2026)"节。关键对照:
> - **K8s 探针**:大厂标准 startup/liveness/readiness 三分离,ESP 当前仅两探针(缺 startupProbe),liveness timeout 1s(已修)。
